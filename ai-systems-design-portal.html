01

Rate Limiting

Core question: How do we control request volume?

Rate limiting controls how many requests a user, application, API key, tenant or service can make in a given time interval. Picture an enterprise AI app with 100,000 registered users, 10,000 concurrent users, an LLM API with limited throughput, expensive GPU inference and agents calling tools. Without limits, a single tenant or runaway automation can consume the entire inference capacity.

Prevent abuse

Stop API abuse and denial-of-service conditions before they reach expensive layers.

Protect capacity

Avoid GPU exhaustion and protect backend and downstream APIs.

Fairness & cost

Allocate resources fairly between tenants and keep inference spend bounded.

Four algorithms

A
Fixed window counter

N requests per window (e.g. 100/min), counter resets each window. Simple, but allows 2× bursts at the boundary: 100 just before reset + 100 just after.

B
Sliding window

Evaluates a continuously moving interval (at 10:00:30, look at 09:59:30–10:00:30). Smoother enforcement, slightly more state.

C · best for LLMs
Token bucket

Tokens refill at a fixed rate; each request spends tokens; capacity permits short bursts. Charge by estimated input + output tokens, not HTTP calls.

D
Leaky bucket

Requests enter a queue drained at a constant rate. Good for smoothing bursty traffic into a steady downstream flow.

Token bucket decision flow (try it in the Labs section)
flowchart LR
  R["Incoming request"] --> E["Estimate cost<br/>input + max output tokens"]
  E --> F["Refill bucket<br/>tokens += rate × elapsed<br/>capped at capacity"]
  F --> C{"tokens ≥ cost?"}
  C -- yes --> D["Deduct tokens"] --> A["Forward to model"]
  C -- no --> X["HTTP 429<br/>+ Retry-After header"]
  A --> RC["Reconcile with actual<br/>token usage after response"]

Check yourself: why is a token bucket better than a request counter for LLM APIs?

Because LLM cost scales with tokens, not requests. One 100k-token prompt costs as much as hundreds of small ones. A token bucket charged by estimated tokens bounds real GPU work and still allows short bursts via bucket capacity.

02

Streaming

Core question: How do we return responses progressively?

Streaming returns data as it is produced instead of waiting for the full response. LLM generation can take several seconds; streaming improves perceived responsiveness because users see output before the answer is complete.

Without vs. with streaming
sequenceDiagram
  participant U as Client
  participant S as API
  participant M as LLM
  Note over U,M: Without streaming
  U->>S: prompt
  S->>M: generate
  M-->>S: full response (after N seconds)
  S-->>U: full response
  Note over U,M: With streaming (SSE)
  U->>S: prompt
  S->>M: generate(stream=true)
  M-->>S: token 1
  S-->>U: data: token 1  (TTFT)
  M-->>S: token 2
  S-->>U: data: token 2  (ITL)
  M-->>S: token N
  S-->>U: data: [DONE]
TTFT
Time to first token

Dominated by queueing + prefill. The number users feel most.

ITL
Inter-token latency

Gap between tokens; governed by decode speed.

TPS
Tokens per second

Generation throughput per stream.

E2E
Total latency

TTFT + (output tokens × ITL), roughly.

Choosing a transport

TechnologyDirectionBest for

from fastapi.responses import StreamingResponse
import asyncio

app = FastAPI()

    tokens = ["AI ", "systems ", "are ", "powerful."]
    for token in tokens:

        await asyncio.sleep(0.2)

Disconnects & cancellation

Detect client disconnects and cancel inference so GPUs stop working on abandoned requests.

Proxy buffering

Disable buffering in NGINX/ALB/middleware; never buffer the full response in middleware.

Heartbeats & errors

Send heartbeats on idle streams; define how partial responses and mid-stream errors are surfaced.

03

Idempotency

Core question: How do we prevent duplicate operations?

An operation is idempotent if executing it multiple times produces the same intended result as executing it once. It is critical in financial systems and for AI agents, which retry tool calls.

The classic failure: an agent sends a payment request → the payment service charges the card → the network times out before confirmation arrives → the agent retries → the customer is charged twice.
Idempotency key turns a dangerous retry into a safe replay
sequenceDiagram
  participant A as Agent
  participant P as Payments API
  participant DB as Idempotency store
  participant G as Gateway
  A->>P: POST /payments  Idempotency-Key: payment-12345
  P->>DB: reserve key (unique constraint)
  DB-->>P: reserved, status=in_progress
  P->>G: charge(amount)
  G-->>P: success
  P->>DB: save status=done + response
  P--xA: response lost (network timeout)
  A->>P: retry, same Idempotency-Key
  P->>DB: lookup key
  DB-->>P: done + stored response
  P-->>A: original response (no second charge)
    
python# Simplified illustration — production needs atomic reservation,
# transactions, payload validation and concurrency control.
def process_payment(key, amount):
    existing = database.get(key)
    if existing:
        return existing.response
    result = payment_gateway.charge(amount)
    database.save(key=key, response=result)
    return result

Design considerations

  • One key per logical business operation
  • Persist the key with a unique database constraint
  • Store operation status (in_progress / done / failed)
  • Store the result to replay on retries
  • Reject reuse of the same key with a different payload (hash the body)
  • Define key expiration and retention
  • Handle in-progress duplicates safely (409 / wait)
  • Make downstream calls idempotent too (pass the key through)

Idempotency for AI agents

A collections agent sends a payment-reminder email, times out, retries — and the customer gets two emails. Derive the key from the business action, not from the LLM output:

keycustomer_id + invoice_id + reminder_type + cycle_id
Payment processingInvoice creationCRM record creationSending emailsSupport casesAgent tool executionWorkflow orchestration
LLM output is not deterministic. Idempotency protects the execution of business operations, not the model's reasoning.

Reject it (e.g. 422). Same key + different payload is a client bug; silently replaying the old response or executing the new one would both be wrong.

04

LLM Serving

Core question: How do we serve models efficiently?

LLM serving is the infrastructure that makes trained models available for inference through APIs: model loading, tokenization, prompt processing, GPU memory management, inference, token generation, streaming, request scheduling, monitoring and scaling.

Inference request lifecycle
flowchart LR
  C["Client"] --> G["API Gateway"] --> AU["AuthN / AuthZ"] --> SC["Request scheduler<br/>queue + batching"]
  SC --> TK["Tokenizer"] --> PF["Prefill<br/>build KV cache"]
  PF --> DC["Decode loop<br/>1 token / step"]
  DC --> ST["Stream tokens"] --> C
  DC -. "reads/writes" .-> KV[("KV cache<br/>GPU memory")]
  PF -.-> KV
Phase A

Prefill

Processes the whole input prompt in parallel and builds the initial key-value (KV) cache. Typically compute-bound; drives TTFT.

Phase B

Decode

Generates output tokens one at a time using the KV cache. Typically memory-bandwidth-bound; drives inter-token latency.

Serving engines

vLLM

High throughput with PagedAttention, continuous batching, efficient KV-cache management.

HF TGI

Hugging Face Text Generation Inference for text-generation workloads.

NVIDIA Triton

Multi-framework inference serving and model deployment.

Ollama

Convenient local model execution and API access for development.

Key serving concepts

ConceptWhat it doesTrade-off

Tensor parallelismSplit each layer's math across GPUsNeeds fast interconnect (NVLink)

KV cacheReuse attention key/value states during generationConsumes large GPU memory per sequence

05

Batching

Core question: How do we process multiple requests efficiently?

Batching groups requests so the GPU does one large matrix operation instead of many small ones. With 100 simultaneous users, sending each request separately wastes most of the GPU; a batch scheduler combines them.

Batch scheduler
flowchart LR
  R1["Request 1"] --> B
  R2["Request 2"] --> B
  R3["Request 3"] --> B
  R4["…"] --> B
  R5["Request 100"] --> B
  B{{"Batch scheduler<br/>max size / max wait"}} --> GPU[["GPU<br/>one batched forward pass"]]

Three types

Static
Wait for N requests

e.g. every 32 requests. High, predictable throughput — but users wait for the batch to fill. Poor for variable traffic.

Dynamic
Size OR time

Dispatch at max batch size 16 or after 10 ms, whichever comes first. Great for embeddings and classifiers.

Continuous
Per-step membership

Requests join and leave the active batch as generation progresses. The standard for LLM serving.

Continuous batching, visualized

Each column is a decode step; a finished sequence frees its slot immediately for a waiting request.

With static batching, slots freed by short requests (A, C) would stay idle until the longest request (B) finished.

Where to use what

WorkloadRecommended approach
LLM generationContinuous batching
EmbeddingsDynamic batching
Document classificationStatic / dynamic batching
Image processingDynamic batching
Offline document ingestionLarge batch processing (and provider batch APIs)
Real-time voiceCarefully bounded micro-batching
Larger batches generally improve throughput but can increase latency and memory pressure. For interactive apps, optimize throughput and TTFT together rather than maximizing batch size blindly.

Caching

Core question: How do we avoid repeated computation?

A RAG request for "What is our refund policy?" embeds the query, searches the vector DB, retrieves documents, builds a prompt and calls the LLM. If thousands of users ask the same thing, doing every step every time is expensive. Caching can apply at each layer.

Cache layers along a RAG request
flowchart TB
  Q["User question"] --> C1{"1 · Exact response cache<br/>hash(prompt + tenant + perms)"}
  C1 -- hit --> OUT["Answer"]
  C1 -- miss --> C2{"2 · Semantic cache<br/>similarity ≥ validated threshold"}
  C2 -- hit --> OUT
  C2 -- miss --> E["Embed query"] -.-> C3[("3 · Embedding cache")]
  E --> R["Vector search"] -.-> C4[("4 · Retrieval cache<br/>re-check perms + freshness")]
  R --> P["Build prompt"] -.-> C5[("5 · Prompt / prefix cache<br/>provider-side")]
  P --> L["LLM generate"] --> OUT
  R -.-> C6[("6 · Database cache<br/>customer / config data")]
1
Exact response

Store final response against an exact key. Best for repeated, deterministic questions.

2
Semantic

Compare question embeddings; "Can I get a refund?" ≈ "What is the refund policy?". Redis vector search, pgvector, vector DBs.

3
Embedding

Cache embeddings for repeated chunks and search queries.

4
Retrieval

Cache vector-search results or doc IDs. Revalidate permissions and freshness.

5
Prompt / prefix

Provider reuses computation for repeated prefixes (system prompts, agent instructions, long docs). Model still generates a new answer.

6
Database

Frequently read customer, account, product and configuration data.

pythoncache_key = hash(tenant_id, permission_scope, user_prompt)  # never just the prompt

    return cache.get(cache_key)

Security boundary. Two users may have different permissions. Never share a cached response across security boundaries — include tenant and permission scope in the key.
Semantic ≠ equivalent. "Cancel my order" and "Cancel my subscription" are similar but not the same. Validate thresholds with evals.

Cache invalidation

One of the hardest problems in distributed systems: if a customer changes their billing address and the old one remains cached, the app returns wrong data.

StrategyDescription

Reliability & Fault Tolerance

Core question: How do we keep systems operational?

Reliability is the ability to keep performing the intended function when individual components fail. An AI system depends on an LLM provider, vector DB, Redis, Salesforce, payments and knowledge services — any of which can be unavailable. Design for failure, don't assume uptime.

Eight reliability patterns

1
Timeout

Never wait indefinitely; derive from the end-to-end latency budget.

2
Retry + backoff

Retry transient errors (timeouts, 429, 503) with exponential backoff and jitter.

3
Circuit breaker

Stop calling a failing dependency; probe before resuming.

4
Fallback

Alternate model, rule-based answer or human — at equal data clearance.

5
Bulkhead

Isolate pools: voice, support and ingestion can't starve each other.

6
Dead letter queue

Park repeatedly failing async jobs for investigation and replay.

7
Graceful degradation

Search down? Serve approved static articles. Model down? Offer a human.

8
Disaster recovery

Backups, multi-region, replication; define RPO and RTO.

pythonimport httpx

async def call_service():
    async with httpx.AsyncClient(timeout=10.0) as client:
        response = await client.get("https://example.com/api")
        return response.json()
delay = min(MaxDelay, BaseDelay × 2n) + jitter
Jitter prevents synchronized retry storms. Don't retry validation (400) or auth (401/403) errors — they need correction, not repetition.

Backpressure & Queue Management

Core question: How do we prevent overloaded services from collapsing?

Backpressure stops a fast producer from overwhelming a slower consumer. An ingestion pipeline receives 100,000 PDFs but the embedding service handles 500/minute — without backpressure, work piles up until memory, queues or downstream services fail.

Bounded ingestion pipeline
flowchart LR

  W --> X["Extraction"] --> E["Embedding service<br/>500 docs/min"] --> V[("Vector DB")]
  Q -- "full" --> RJ["429 / throttle /<br/>load shedding"]
  W -- "repeated failure" --> DLQ[["Dead letter queue"]]
  E -. "slow / saturated signal" .-> W
Queue size limits

Bounded, never infinite.

Consumer concurrency

Cap workers to downstream capacity.

Reject / throttle

Fail fast with 429 rather than time out.

Adaptive concurrency

Adjust limits from observed latency.

Prioritization

Interactive before batch.

Dead-letter queues

Isolate poison messages.

Load shedding

Drop low-value work under stress.

Little's Law

Items in system = arrival rate × time in system.

Cost Optimization

Core question: How do we control inference and infrastructure costs?

A successful AI product can become financially unsustainable. 100,000 users × 10 requests/day × (1,000 input + 500 output tokens) is:

1 MAI requests / day
1 Binput tokens / day
500 Moutput tokens / day

These illustrate scale, not a cost estimate. Plug your own prices into the cost lab below.

Seven levers

1
Model routing

Smaller models for simpler tasks.

2
Prompt optimization

Remove unnecessary context.

3
Semantic caching

Reuse suitable prior results.

4
Retrieval optimization

Fewer, better chunks.

5

Offline workloads at batch rates.

6

Cheaper self-hosted inference.

7
Token budgets

Cap input and output lengths.

+
Prefix caching

Discounted reuse of long, stable prompts.
